# 代码风格指南

> 本文档用于统一 EnglishAgent 项目的代码组织、设计模式、接口格式、错误处理和测试规范。新增模块、扩展接口、重构页面时，优先遵循本文档；如果本文档与现有模块冲突，以“保持现有模块一致性”为第一原则，并在重构时逐步收敛。

## 1. 总体原则

1. 代码先表达业务，再表达技巧。命名、函数边界和数据结构应让读者能快速看出模块意图。
2. 新功能优先复用现有模式：`backend/routers` 定义接口，`backend/db.py` 或服务层处理数据与业务，`frontend/src/utils/api.js` 统一封装请求，页面组件只负责状态和交互。
3. 接口契约要稳定。后端响应字段、前端 API 函数、测试用例必须一起更新。
4. 错误提示对用户使用中文，对开发者保留必要 detail。
5. 每个大功能至少包含后端测试或前端构建验证；涉及接口契约时必须补测试。

## 2. 后端代码风格

### 2.1 目录职责

- `backend/app.py`：FastAPI 应用入口、CORS、静态资源挂载、路由注册。
- `backend/routers/*.py`：HTTP 层，负责鉴权、参数校验、调用服务/DAO、组装响应。
- `backend/services/*.py`：业务服务层，放置可复用业务逻辑、外部能力适配、复杂策略。
- `backend/tasks/*.py`：异步/定时任务逻辑。
- `backend/db.py`：SQLite DAO 与兼容性迁移兜底。
- `migrations/*.sql`：正式数据库结构变更。

### 2.2 Router 规范

每个路由文件保持以下顺序：

1. 标准库 imports。
2. 第三方 imports。
3. 项目内部 imports。
4. `router = APIRouter()`。
5. Pydantic request/response model。
6. 模块内私有 helper。
7. endpoint 定义。

Endpoint 必须声明 `response_model`，除非返回动态结构或文件流。

```python
class ListeningTTSRenderRequest(BaseModel):
    text: str
    lang: str = "en"
    voice: str = "M1"
    speed: float = 1.0


class ListeningTTSRenderResponse(BaseModel):
    audio_url: str
    cached: bool = False
    backend: str = ""
    duration: Optional[float] = None


@router.post("/tts/render", response_model=ListeningTTSRenderResponse)
async def render_listening_tts(
    payload: ListeningTTSRenderRequest,
    current_user: dict = Depends(get_current_user),
):
    ...
```

### 2.3 鉴权与用户隔离

需要登录的接口统一使用：

```python
current_user: dict = Depends(get_current_user)
```

涉及用户数据时必须校验 `user_id`：

```python
user_id = str(current_user.get("id") or "")
if not user_id:
    raise HTTPException(status_code=400, detail="User ID not found")
```

读取单条资源时必须校验资源所有权：

```python
row = get_resource(resource_id)
if not row:
    raise HTTPException(status_code=404, detail="Resource not found")
if str(row.get("user_id")) != user_id:
    raise HTTPException(status_code=403, detail="Access denied")
```

### 2.4 Pydantic 模型命名

- 请求模型：`<Module><Action>Request`
- 响应模型：`<Module><Action>Response`
- 列表项模型：`<Module><Entity>Item`
- 简单实体模型：`<Entity>`

示例：

- `ReminderBatchStatusUpdateRequest`
- `ReminderBatchStatusUpdateResponse`
- `ReminderPreferenceHistoryItem`
- `ListeningQuizQuestion`

### 2.5 字段命名

后端 API JSON 字段统一使用 `snake_case`：

- `audio_url`
- `scheduled_at`
- `question_type`
- `reminder_ids`

前端如果需要使用 camelCase，可以在页面层或 API 层做转换，但请求/响应契约以后端 `snake_case` 为准。

### 2.6 错误格式

后端错误统一使用 FastAPI 标准：

```python
raise HTTPException(status_code=400, detail="reminder_ids不能为空")
```

推荐状态码：

- `400`：参数非法、状态不允许、缺少必填字段。
- `401`：未登录或 token 无效，由鉴权层处理。
- `403`：资源不属于当前用户。
- `404`：资源不存在。
- `500`：服务端不可恢复异常。

面向用户的常见错误尽量写中文；系统级错误可保留英文，但前端必须做中文兜底。

## 3. 设计模式使用规范

### 3.1 Router + Schema + Service + DAO

这是后端主要模式。

- Router：处理 HTTP 和权限。
- Schema：定义请求/响应格式。
- Service：处理复杂业务策略、外部系统适配、缓存、状态机。
- DAO：读写数据库。

适用场景：

- 新增学习模块。
- 新增第三方能力，如 TTS、ASR、支付、导入导出。
- 业务逻辑超过 80 行或会被多个 endpoint 复用。

### 3.2 Adapter 模式

外部能力必须通过服务层适配，不要在 router 中直接调用第三方 SDK。

示例：[tts_service.py](../backend/services/tts_service.py)

`LocalTTSService` 对外只暴露 `health()` 和 `synthesize()`，内部可以选择 `supertonic` 或 fallback，不影响调用方。

适用场景：

- TTS / ASR / LLM / 支付 / 文件存储。
- 需要本地 fallback。
- 未来可能替换供应商。

### 3.3 Strategy 模式

存在多种策略时，用显式 key 和配置字典表达，不要散落 if/else。

示例：

- 提醒策略预设：`balanced`、`high_focus`、`gentle`
- 听力精听模式：`mixed`、`dictation`、`keyword`
- 词汇训练模式：`cloze`、`recall` 等

要求：

- key 使用稳定英文小写。
- 展示文案放在前端映射或后端 preset 元数据里。
- 新增策略必须补测试。

### 3.4 Factory / Singleton

昂贵或全局共享资源使用轻量工厂函数获取。

```python
_TTS_SINGLETON = LocalTTSService()


def get_tts_service() -> LocalTTSService:
    return _TTS_SINGLETON
```

适用场景：

- 模型加载。
- 本地缓存。
- 外部客户端。

测试时通过 `monkeypatch` 替换模块内实例。

### 3.5 State Store

当前项目部分模块使用内存 runtime store，例如：

- `AUDIO_QUIZ_RUNTIME`
- `LISTENING_INTENSIVE_RUNTIME`
- `SPEAKING_PRACTICE_RUNTIME`

使用规则：

- 必须记录 `user_id` 并校验用户隔离。
- 只用于短生命周期会话。
- 重要结果必须落库。
- 未来需要跨进程部署时，应迁移到数据库或 Redis。

## 4. API 设计规范

### 4.1 URL 命名

统一使用资源名 + 动作：

```text
GET    /reminder
POST   /reminder
PUT    /reminder/{reminder_id}/status
POST   /reminder/batch/status
GET    /listening/tts/health
POST   /listening/tts/render
```

规则：

- 资源使用单数模块前缀：`/listening`、`/speaking`、`/reminder`。
- 批量操作放在 `/batch/...`。
- 当前用户配置使用 `/me`。
- 健康检查使用 `/health`。
- 生成类动作使用 `/generate` 或 `/render`。

### 4.2 请求格式

POST/PUT 请求统一使用 JSON body：

```json
{
  "reminder_ids": ["id_1", "id_2"],
  "status": "pending"
}
```

查询类接口使用 query params：

```text
GET /reminder/audit/logs?limit=80&action=batch_delete
```

### 4.3 响应格式

单对象响应直接返回对象：

```json
{
  "audio_url": "/media/tts/demo.wav",
  "cached": false,
  "backend": "supertonic",
  "duration": 1.2
}
```

列表响应直接返回数组：

```json
[
  {
    "id": "audio_001",
    "title": "IELTS Listening Practice Test 1",
    "difficulty": "easy"
  }
]
```

批量操作必须返回统计和明细：

```json
{
  "total": 3,
  "updated": 2,
  "skipped": 1,
  "failed": 0,
  "updated_ids": ["id_1", "id_2"],
  "skipped_ids": ["id_3"],
  "failed_ids": []
}
```

### 4.4 分页与限制

列表接口至少提供 `limit`，必要时提供 `offset`。

后端必须限制最大值：

```python
limit=max(1, min(500, int(limit)))
```

## 5. 数据库与迁移规范

### 5.1 迁移脚本

结构变化优先添加 `migrations/<序号>_<说明>.sql`。

命名示例：

```text
017_reminder_preference_history.sql
```

### 5.2 兼容性兜底

如果历史库可能缺字段，可在 `init_db()` 或 DAO 内使用 `CREATE TABLE IF NOT EXISTS`、`ALTER TABLE ... ADD COLUMN` 做兼容兜底。

要求：

- 兜底逻辑必须幂等。
- 不允许破坏已有数据。
- 删除字段或清空表必须单独评审。

### 5.3 JSON 字段

SQLite 中复杂字段以 JSON 字符串存储：

- 写入时 `json.dumps(..., ensure_ascii=False)` 优先。
- 读取时统一转换成 dict/list 后再返回。
- 空值返回 `{}` 或 `[]`，不要返回 JSON 字符串给前端。

## 6. 前端代码风格

### 6.1 API 层

所有 HTTP 请求统一写在 [api.js](../frontend/src/utils/api.js)。

页面组件不得直接使用 `axios`。

API 函数命名：

- 获取：`getXxx`
- 创建/生成：`createXxx`、`generateXxx`
- 更新：`updateXxx`
- 删除：`deleteXxx`
- 批量：`batchXxx`
- 提交：`submitXxx`

示例：

```javascript
export const renderListeningTTS = async ({ text, lang = 'en', voice = 'M1', speed = 1.0 }) => {
  const response = await api.post('/listening/tts/render', {
    text,
    lang,
    voice,
    speed,
  }, { headers: getAuthHeader() });
  return response.data;
};
```

### 6.2 错误处理

接口错误统一通过 `normalizeUiError` 做中文化。

页面层兜底：

```javascript
catch (e) {
  setError(typeof e === 'string' ? e : '操作失败');
}
```

新增常见后端错误时，同步更新 `ERROR_MESSAGE_MAP`。

### 6.3 页面组件

页面组件组织顺序：

1. imports。
2. 模块常量。
3. `function PageName()`。
4. route/nav 配置。
5. `useState`。
6. `useMemo` / derived state。
7. 数据加载函数。
8. 事件处理函数。
9. `useEffect`。
10. JSX。

页面组件应保持“薄业务”：

- 可以处理表单状态、筛选、展示映射。
- 不应包含复杂算法。
- 复杂转换放到 helper 或服务层。

### 6.4 UI 文案

- 用户可见文案使用中文。
- 后端枚举值可以显示为英文 key，但页面应优先映射成中文。
- 状态类展示使用映射表：

```javascript
const STATUS_LABEL_MAP = {
  pending: '待发送',
  sent: '已发送',
  failed: '发送失败',
};
```

### 6.5 样式

- 优先复用 `frontend/src/App.css` 中已有页面风格。
- 页面级样式使用模块前缀，例如 `.reminder-*`、`.vocab-*`。
- 控件样式优先复用现有 class，例如 `plan-input`、`plan-filter-btn`。
- 新样式必须考虑移动端断点。

## 7. 测试规范

### 7.1 后端测试

新增接口至少覆盖：

- 成功路径。
- 用户隔离。
- 参数非法。
- 关键副作用，如错题入库、审计日志、缓存、状态更新。

当前核心回归文件：

```text
tests/test_week2_backend_progress.py
```

测试命名：

```python
def test_<module>_<behavior>(isolated_db):
    ...
```

### 7.2 前端验证

每次改前端必须运行：

```bash
npm --prefix frontend run build
```

如果是交互或布局改动，应启动前端并人工验证关键路径。

### 7.3 常用验证命令

```bash
PYTHONPATH=. ./venv/bin/pytest -q tests/test_week2_backend_progress.py
npm --prefix frontend run build
```

## 8. 文档同步规范

以下变更必须同步文档：

- 新增或修改 API：更新 [API接口文档](API接口文档.md)。
- 新增大模块：更新 [开发进度文档](开发进度文档.md) 和 [ATENGS.md](../ATENGS.md)。
- 新增 UI 规范：更新 `docs/UI/` 对应文档。
- 新增测试策略：更新 [测试计划文档](测试计划文档.md)。

## 9. 提交前检查清单

1. 接口是否有 `response_model`。
2. 用户数据是否校验 `user_id`。
3. 前端是否通过 `utils/api.js` 调接口。
4. 错误提示是否中文化。
5. 是否更新相关文档。
6. 是否补充或更新测试。
7. 是否运行必要验证命令。
